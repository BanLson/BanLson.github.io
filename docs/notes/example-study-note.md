# 示例：用四步法整理主题笔记

<div class="example-notice">
  <strong>示例文章</strong>
  <span>本文用于展示学习笔记的写作与排版方式，内容为通用方法，不代表 BanLson 的个人经历。</span>
</div>

很多学习笔记最后会变成一堆摘抄：当时看懂了，过一段时间却想不起重点。一个简单的改进办法，是在动笔前先确定笔记的结构。

下面这套「四步法」适合整理一个独立主题，例如「HTTP 缓存」「Git 分支模型」或「React 状态管理」。它不能替代系统学习，但可以让笔记更容易回看和复用。

## 第一步：写下要解决的问题

先不要急着抄定义，用一两句话写下：

- 我为什么学这个主题？
- 我希望学完后能做什么？
- 现在最困惑的地方是什么？

问题会决定笔记的边界。比如学「HTTP 缓存」，如果目标只是「看懂响应头」，就不必把整个 HTTP 协议都塞进来；如果目标包含「排查线上缓存不生效」，那么排查步骤就应该成为重点。

> 一个实用判断：如果一条信息删掉后不影响回答开头的问题，它可能不属于这篇笔记。

## 第二步：用自己的话解释概念

概念部分建议包含三样东西：

1. **一句话定义**：尽量不用原文，逼自己重新组织语言。
2. **关键词拆解**：把定义里不熟悉的词继续解释，直到没有循环定义。
3. **来源与版本**：记录参考文档的链接和阅读时间，方便以后核对。

例如，解释「缓存命中率」时，可以先写成：

> 缓存命中率是指请求缓存时，缓存中已经有所需内容的次数占总请求次数的比例。

然后再补充：命中时通常更快，未命中时可能要回源；统计口径不同，结果也会不同。这样比单纯抄一句定义更容易理解。

### 概念卡片的写法

每个概念可以用一个小卡片结构记录：

| 字段 | 作用 |
| --- | --- |
| 名称 | 概念的标准叫法 |
| 一句话解释 | 用自己的语言概括 |
| 易混淆点 | 和哪些概念容易混 |
| 例子 | 一个最小例子 |
| 来源 | 文档、书籍或课程链接 |

## 第三步：给出可验证的例子

例子是笔记里最值得保留的部分。好的例子通常具备这些特点：

- 足够小，能在一屏内看完
- 可以运行、复现或验证
- 能说明一个关键点，而不是覆盖所有情况
- 包含输入和预期输出

以学习命令行工具为例，与其写「这个命令用于查看文件」，不如写清楚：

```bash
# 查看当前目录下每个文件的大小，并按从大到小排序
ls -lhS
```

再补充：在什么系统、什么 shell 下验证过；如果输出与预期不同，可能是什么原因。

::: tip 例子不必一次写完
第一遍学习时先记录最小例子，等真正用过一次，再把实际遇到的问题补进来。笔记会随着使用逐渐变得可靠。
:::

## 第四步：写下下一步行动

结尾不要只写「已学完」。可以留一个行动清单：

- ☐ 用自己的话复述一遍核心概念
- ☐ 跑通文中的最小例子
- ☐ 找一个真实场景套用
- ☐ 一周后不看笔记，尝试回答开头的问题
- ☐ 把仍然不清楚的问题拆成下一篇笔记

行动项要具体到可以判断是否完成。例如「多练习」很难执行，「用 10 条测试数据跑一遍并记录结果」就容易执行得多。

## 一个可以直接复制的模板

```md
# 主题名称

## 我想解决的问题

- 为什么学：
- 学完能做什么：
- 当前困惑：

## 核心概念

### 概念 A

- 一句话解释：
- 易混淆点：
- 最小例子：
- 来源：

## 可验证的例子

（代码、步骤、输入与预期输出）

## 行动清单

- ☐ 复述核心概念
- ☐ 跑通例子
- ☐ 套用到真实场景
- ☐ 一周后自测

## 遗留问题

- 
```

## 怎么判断笔记是否合格

可以用下面几个问题自查：

1. 不看原文，能否回答开头提出的问题？
2. 例子是否足够小，并且真的验证过？
3. 概念之间是否有清楚的边界？
4. 是否记录了来源和版本？
5. 是否留下了下一步行动？

如果只能做到其中一部分，也没关系。笔记是持续修改的文档，不是一次性的作业。先把结构搭起来，再在使用中补全，通常比一次写得很长更容易坚持。
